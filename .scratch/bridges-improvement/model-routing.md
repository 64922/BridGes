## 二、执行策略

### 1. 双终端并行（默认形态）

- **终端 A（kimi k3）**：只处理上表 kimi 组 issue，只改 `apps/web/` 与前端 E2E 测试。
- **终端 B（deepseek v4）**：只处理 v4 组 issue，只改 `src/`、后端测试与契约测试。
- 两终端可同时运行；各自完成后独立提交（提交信息：`Issue NN 完成：<一句话>`，与仓库现有风格一致）。
- 提交后把对应 issue 文件 `Status:` 从 `ready-for-agent` 改为 `ready-for-human`（与 01-06 已完成项一致）。

### 2. 文件域隔离（防 git 冲突）

- kimi 与 v4 的文件域天然分离：`apps/web` vs `src/` + `tests/`。
- **同模型侧串行**：kimi 组各 issue 都改同一 `apps/web`，v4 组都改同一 `src/`——同一终端内一次只认领一个 issue，完成后提交再开下一个，避免同文件域并行冲突。
- 均衡组的接力：v4 提交 API + 契约测试后再交给 kimi 接 UI，两段各自独立提交。

### 3. 关键路径与开工顺序（首个并行窗口）

首个窗口可同时开工（互不依赖）：

- **终端 B（v4）优先启动**：
  1. **17**（索引，纯后端、无人阻塞）→ 是 18/20 的前置，越早越好
  2. **10**（凭据与探测）→ 是 11/30/31/32 的前置
  3. **07 后端段**（认证 API）→ 解锁均衡组
- **终端 A（kimi）优先启动**：
  1. **12**（外壳与侧栏，前端基座）→ 是 13/18/24/38 的前置
  2. **13**（输入区与空白态）→ 是 14/36 的前置

依赖提醒：kimi 的 18/24 依赖 v4 的 17；kimi 的 36/38 依赖大量 v4 issue。**v4 始终领先 2-3 个 issue 是健康的节奏**，kimi 侧不会空等。

### 4. 可选加速（三终端）

想进一步并行时，加一个终端 C（v4 或 kimi），但须遵守：

- 同模型两个终端选择**文件域不重叠**的 issue（如 v4 的 17 与 10 可并行——一个碰 `ingestion/`，一个碰 `credentials/`；kimi 的 12 与 25 可并行——一个碰 shell，一个碰 profile 页）。
- 同模型两个终端**不得同时跑全套测试**（pytest 共享 `bridges.db`/对象目录，E2E 共享浏览器与端口）——测试验收错峰执行。

### 5. 每个 issue 的完成门（沿用 issue 内 Verification 块）

- 后端：`pytest -k <该 issue 关键词>` + `ruff check .` + `mypy src`
- 前端：`npm --prefix apps/web run typecheck` + `build` + `test:e2e -- --project=chromium`
- 涉及真实 Key/网络冒烟的条目：只在显式人工冒烟环境中跑，不得要求自动测试携带 Key（沿用 02 建立的 `*_FILE` 显式启用路径）。
- 双终端同时完成时，最终全量回归（完整 pytest + 完整 E2E）串行执行一次，由任一终端负责，避免共享资源竞争。

### 6. 跨终端交接与验收

- 均衡组接力后，由最后接手的一方跑该 issue 的完整 Verification。
- v4 侧新增后端行为时，同步补充契约测试，kimi 侧以契约测试为对接界面，不猜接口。
- 39/41 是全量收口项，只有大部分 07-38 落定后才开工，不适合早期并行。

## 三、风险清单

| 风险 | 规避方式 |
|---|---|
| 同文件域并行导致合并冲突 | 同模型串行；三终端时按子目录分离 |
| 双终端同时跑测试竞争共享资源（db/端口/浏览器） | 测试错峰；全量回归只由一个终端串行跑 |
| 前端空等后端 | v4 领先 2-3 个 issue；kimi 侧先做 12/13 基座 |
| 均衡组接口漂移 | v4 先出契约测试，kimi 按契约对接 |
| 双终端各自提交导致测试基线不稳 | 每个提交前确保该 issue 的 Verification 通过 |
