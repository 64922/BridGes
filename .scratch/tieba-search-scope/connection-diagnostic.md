# 已登录浏览器的连接诊断

日期：2026-10-07（Asia/Shanghai）。

用户已在 Chrome 打开华东交通大学吧并装载 ChatGPT 扩展；之前在 Edge 已确认登录且可浏览。

本轮 Codex 浏览器工具能发现 Chrome 与 Edge 的扩展实例，读取两者标签页均返回 `nodeRepl.fetch request failed`。重置工具会话之后仍复现；选择 Chrome 成功，但为会话命名／读取用户标签页的调用失败，因此尚未实际读取网页或搜索讨论。

只读检查 Codex 当日本地日志，发现当前聊天的内置浏览器查询报告 `No ChatGPT browser route is available for browser session`；同时有其他连接层的 WebSocket 错误。它们是诊断线索，不能据此断定 Chrome 扩展损坏，也不把内置浏览器的错误等同于 Chrome 的直接原因。没有修改应用配置、浏览器权限、凭据或插件缓存。

用户确认 Chrome 侧边聊天可以正常使用；再次尝试当前聊天读取标签页仍失败。这证明部分扩展连接可用，不能宣称当前聊天已获得浏览器控制。

官方文档要求从聊天的 `@` 菜单关联浏览器；故障排查还要求确认桌面应用“设置 → 电脑使用”对应浏览器显示“管理”，必要时重启桌面应用或用新的聊天清除连接状态。来源：[浏览器扩展文档](https://learn.chatgpt.com/docs/chrome-extension)。本轮请求用户先在当前聊天的 `@` 菜单选择 Chrome，再恢复验证；暂不修改本机设置或结束应用。

用户随后发送真实 Chrome 插件关联 `plugin://browser@openai-bundled?browserFamily=chrome`。关联后分别核验会话命名、直接 `user.openTabs()` 与按固定目标 URL 的 `cua.getTab()`，均返回同一连接错误。不能再把故障归因于没有装扩展、侧栏未加载或用户没有选择 Chrome；下一步需要重启桌面应用恢复控制连接（官方建议的恢复步骤，尚未执行，不能保证必然有效）。

本轮只将结果卡片中的“Edge 登录会话”改为“浏览器中的登录会话”，避免用户换用 Chrome 后出现错误文案；卡片的十二项针对性测试通过，lint 与生产构建通过。浏览器取证路径依然未完成。

应用源码修复与浏览器工具连接独立：安装 ChatGPT 扩展不会自动让 BridGes 后端使用浏览器登录会话。恢复工具连接后，仍须观察实际吧内搜索流程并实现、验证模块的登录态取证路径。

后续：用户重启后扩展仍不可控，随后明确授权 Playwright 专用会话。人工通过验证后可浏览未登录帖子，登录后吧内搜索与更多回复可用。已验证隔离目录持久化、真实原生搜索与新版 DOM 读取，并接入 BridGes 的账户绑定取证。扩展传输故障仍未修复，但模块已不依赖扩展；后端不会自动使用日常浏览器的会话。
