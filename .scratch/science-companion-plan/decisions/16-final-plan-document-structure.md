# 最终《科教智能体项目规划书》章节编排、图表与附录结构

形成日期：2026-07-24  
状态：已确认  
适用范围：最终项目规划书的编排、交叉引用、覆盖验证和汇编

## 1. 结论

最终规划书应采用：

> **A“决策与系统蓝图”作为正文骨架 + B“科学成长旅程”作为贯穿式黄金路径 + C“评分证据与验收”作为覆盖矩阵和章节证据框。**

不采用单纯按比赛评分项写正文，也不采用把十五项既有决策原样顺序拼接的方式。

- 只按评分项组织会造成同一系统能力在多个评分章节重复出现，难以指导开发；
- 只按用户旅程组织会弱化权限、数据、部署、迁移和评测等横切合同；
- 直接拼接既有研究会重复定义术语、技术栈和质量门，并留下跨文档冲突。

正文以“方向 → 产品 → 可信智能 → 工程 → 质量演进”递进；每个重要章节同时回答：

1. 为什么需要；
2. 用户和业务怎样工作；
3. 领域对象与边界是什么；
4. 系统如何实现；
5. 失败和降级怎样处理；
6. 如何验证已满足。

## 2. 三种结构原型

### A：决策与系统蓝图（推荐正文骨架）

以稳定决策和开发依赖为顺序：

`方向与约束 → 产品与体验 → 可信智能 → 工程实现 → 质量与演进`

优点：

- 每个概念有唯一规范性归属；
- 产品、研发、专家、安全和运维都能找到自己的权威章节；
- 技术架构、迁移、部署和评测不会被“用户旅程”埋没；
- 最适合直接指导成熟项目开发。

局限：

- 若没有贯穿案例，读者可能把各章看成孤立模块；
- 与比赛评分项的关系需要额外覆盖矩阵。

### B：科学成长旅程

以一个认证用户从学习使命到可信产物、反馈演进和长期陪伴的全过程为顺序：

`注册登录 → 建立项目 → 编译画像切片 → 组织证据 → 学习/表达/多模态 → 质量门 → 协作发布 → 反馈更新`

优点：

- 能把数字分身与有人味科学表达解释为一个完整产品；
- 适合产品、设计、教学专家和新加入团队快速建立共同理解；
- 容易呈现正常、冲突、撤权和降级路径。

局限：

- 同一个基础能力会在多个旅程步骤重复；
- 很难单独承载数据库、迁移、供应链、部署和容量的完整规范。

因此 B 不独立承担正文，而是转化为正文前部的黄金路径，以及各章固定的“本章在黄金路径中的位置”。

### C：评分证据与验收

以科学价值、技术深度、应用潜力、复现与工程成熟度为主轴，把要求映射到功能、设计、实现和证据。

优点：

- 能明确证明比赛要求没有遗漏；
- 能连接基线、消融、评测、硬门和复现命令；
- 适合作为审查和阶段验收入口。

局限：

- 容易为了评分重复叙述系统；
- 评分维度不是稳定架构边界；
- 不适合作为团队长期实现手册。

因此 C 转化为开篇覆盖矩阵、章节末证据框和附录中的完整追踪表。

## 4. 章节权重规则

权重用于防止“愿景过长、实现过短”或“技术栈堆砌、产品闭环缺失”，不是最大页数。

| 部分 | 建议权重 | 原因 |
|---|---:|---|
| 第一部 方向与约束 | 10% | 快速建立共同语境和要求追踪，不重复后文细节 |
| 第二部 产品与体验 | 27% | 展示真实用户价值、完整功能和科学成长闭环 |
| 第三部 可信智能与治理 | 27% | 承载项目最核心的科学、个性化、智能体和治理深度 |
| 第四部 工程与生产 | 23% | 确保架构、数据、安全和部署能直接指导开发 |
| 第五部 评测与演进 | 13% | 证明质量主张、开发路线和成熟发行资格 |

附录、术语表、来源和机器可读合同不计入上述正文权重，不得为控制篇幅删除必要内容。

每章内部建议按以下比例组织：

- 10%：本章目标、范围和非目标；
- 20%：用户/业务行为与主流程；
- 30%：领域对象、合同、状态和规则；
- 25%：系统实现、失败、迁移与治理；
- 15%：验收、指标、测试和引用。

纯产品章节可提高用户流程比重，纯工程章节可提高合同与实现比重，但每章必须保留验收段。

## 5. 黄金路径的使用方式

正文只维护一组具名黄金路径，不在各章重新编造案例：

1. **个性化学习**：注册用户建立学习使命，使用可信资源完成短课和练习，以证据更新学习路径；
2. **科学表达**：用户从项目证据生成科普/讲稿/汇报/论文辅助，经事实锁和人味复查发布；
3. **多模态创作**：用户把科学材料转为结构化分镜、可编辑媒体和无障碍产物；
4. **画像治理**：系统提出候选画像，用户确认、冻结、纠正或删除，并观察回答变化；
5. **协作与治理**：个人对象最小复制到共享项目，经历评论、审批、领域包规则和发布门；
6. **失效与恢复**：来源、授权、领域包或索引失效后，系统阻断新使用、定位影响并重新验证。

每章开头用一个短框标记：

- 本章参与哪些黄金路径；
- 输入和输出对象；
- 上游/下游章节；
- 本章的失败闭锁点。

黄金路径只解释连接关系；规范性规则仍保存在唯一权威章节。

### 6.2 三类内容标签

最终规划书使用三种显式标签：

- **规范**：必须遵守的稳定边界、状态、合同和门；
- **示例**：帮助理解但不形成额外规则的案例或伪代码；
- **时效快照**：模型版本、价格、限流、外部接口和工具限制，必须标核验日期。

示例不能静默变成规范，时效快照不能散落在多个章节。

### 6.3 交叉引用

- 每章使用稳定章节 ID，例如 `P3-C13`；
- 需求使用 `REQ-*`，风险使用 `RISK-*`，合同使用 `CONTRACT-*`，图表使用 `FIG-*`；
- 第一次出现术语时链接术语表；
- 复述超过两句话时改为摘要 + 权威章节链接；
- 冲突时以正文中的唯一规范性归属为准，附录不得创建新规则；
- 来源和决策记录必须指向原研究或一手依据，不用无来源总结替代。

## 11. 文档质量门

最终规划书只有同时满足以下条件才算完成：

1. 十五项已解决决策均进入覆盖矩阵；
2. 比赛与用户硬约束均有唯一正文落点和验收证据；
3. 每个规范概念只有一个权威章节；
4. 正文不复制研究全文，而是综合、裁决和交叉引用；
5. 稳定规则、示例和时效快照明确分离；
6. 每章包含范围、对象/合同、异常、验收和引用；
7. 图表有编号、正文解释和无障碍等价表达；
8. 技术版本、价格和限制标核验日期；
9. Conda `agent` 只出现在本地开发语境；
10. 手动分进程、统一 CLI、Docker、Podman 语义一致；
11. 不含作品演示、比赛答辩、宣传或路演内容；
12. 不以篇幅为由裁剪成熟产品能力；
13. 术语与 `CONTEXT.md` 一致；
14. 所有本地和外部引用可解析；
15. 附录不创建与正文冲突的新规范；
16. 由产品、科学、教学、安全、数据、无障碍、工程和运营视角分别完成覆盖审查。
