# 领域包专家工作台与发布流程

形成日期：2026-07-24  
状态：已确认  
适用范围：八类首批领域包及后续第三方领域包

## 1. 结论

领域包专家工作台应是一个**职责分离的可审查发行流水线**，不是带“批准”按钮的内容管理后台。

确认采用：

> 以方案 A“阶段控制台”为主框架，吸收方案 B 的语义 Diff 工作面板和方案 C 的责任泳道、失效影响带。

任何正式发行都必须同时满足：

1. 内容维护者对规范化包摘要提交内容签名；
2. 独立复核者在重跑夹具、抽查来源和核验安全下限后提交独立验证签名；
3. 平台发行者验证前两种身份不同、资质适用、利益冲突可接受、依赖闭包、沙箱、评测和灰度结果后追加发行签名；
4. H3 高风险变更还要有合资格领域专家与安全/治理责任人联合签名；
5. 所有签名绑定同一 Manifest、内容树、依赖锁、夹具摘要、构建出处和语义 Diff；任何内容变化都会使旧签名失效。

安全管理员可以立即隔离、暂停或紧急撤销，但不能编辑科学规则、代替复核者或直接发布。回滚不是把数据库恢复到旧状态，而是将上一个仍受信的版本重新设为项目可选版本，并保留撤销、迁移、影响和责任链。

## 2. 三种状态不得混合

### 2.1 包治理状态

沿用既定状态：

`DRAFT → IN_REVIEW → SIGNED → ACTIVE → DEPRECATED`

异常状态：

- `SUSPENDED`：状态未知、评测回归或可恢复问题；
- `REVOKED`：签名、供应链、安全或严重科学缺陷；
- `EXPIRED`：复核有效期到期。

包文件不能自行改变治理状态；只有平台状态机和授权角色可以。

### 2.2 复核流程阶段

这是工作台流程，不替代包治理状态：

1. 编写与预检；
2. 提交内容签名；
3. 分配独立复核；
4. 复核与异议；
5. 平台发行预检；
6. 灰度验证；
7. 发行签名与激活；
8. 监测、失效或取代。

### 2.3 失效事件状态

`DETECTED → TRIAGED → CONTAINED → IMPACTED_OBJECTS_FOUND → REMEDIATING → REVALIDATING → CLOSED`

紧急撤销允许先进入 `CONTAINED`，但不能跳过后续双人复核、影响报告和透明记录。

## 4. 信息架构

### 4.1 全局包头

始终显示：

- 包名、版本、治理状态和风险级别；
- 当前流程阶段、负责人和下一责任人；
- 内容摘要、依赖锁摘要和最后一次构建；
- 维护者签名、独立验证签名、平台发行签名；
- 阻塞数量、过期来源、夹具覆盖、受影响下游；
- 当前用户角色、资质适用范围和利益冲突声明状态。

### 4.2 左侧工作区导航

1. 总览与待办；
2. 范围、排除项和 Manifest；
3. 来源与状态解析；
4. 问题类型、Claim Schema 和证据映射；
5. 规则与措辞策略；
6. 确定性校验器和能力需求；
7. 夹具与沙箱结果；
8. 语义 Diff 与判定差异；
9. 依赖、迁移和下游影响；
10. 资质、角色和利益冲突；
11. 独立复核与少数意见；
12. 灰度、发行与透明记录；
13. 失效、撤销、回滚和重验证。

### 4.3 主工作面

使用三栏：

- 左：流程阶段、对象树或责任泳道；
- 中：当前任务编辑/比较/审查画布；
- 右：来源依据、规则解释、质量门、签名和审计检查器。

普通用户不进入本工作台；产品前台只显示包版本、关键来源状态、措辞限制、人工 override 和公开发行记录，不显示专家证件或不必要的利益细节。

## 5. 关键对象

- `DomainPackManifest`：规范化包清单；
- `DomainRule`：可执行规则与自然语言解释；
- `SourcePolicy`：来源角色、适用范围、状态接口和失败语义；
- `ValidatorRequirement`：逻辑能力、输入输出和隔离级别；
- `FixtureCase/FixtureResult`：金样与运行结果；
- `SemanticDiff`：结构、规则、判定、措辞和迁移差异；
- `PackDependencyLock`：精确依赖闭包；
- `MigrationReport`：旧记录到新记录的映射及待人工项；
- `QualificationRecord`：资质类型、核验、有效期和适用范围；
- `ConflictOfInterestDeclaration`：逐版本利益声明；
- `ReviewAttestation`：内容或独立验证签名；
- `ConflictDisclosure`：少数意见与未决依据；
- `PackRelease`：发行摘要、平台签名和透明记录；
- `InvalidationEvent/RevocationEvent`：失效、控制和影响传播；
- `ImpactSet`：受影响包、运行、Claim、Evidence、Wording、产物和项目。

## 6. 关键交互

### 6.1 来源注册

向导要求依次填写：

1. 稳定标识和来源主体；
2. 它对什么问题、对象和 evidence role 有权威；
3. 明确不能支持什么结论；
4. 正文/元数据版本和生命周期状态接口；
5. 超时、缺字段、查无记录、冲突的失败语义；
6. 更新预算和人工核验兜底；
7. 正例、版本变化、撤回和状态未知夹具。

只登记机构名称或 URL 不能完成注册。

### 6.2 规则与措辞编辑

同屏展示：

- 结构化条件、输入、输出、拒绝码和 unknown 处理；
- 给专家阅读的自然语言说明；
- 来源版本与精确定位；
- 允许/禁止措辞；
- 对应夹具和人工门级别；
- 平台下限对照。

若自然语言与结构字段不一致，预检直接阻断。

### 6.3 校验器配置

专家只能选择能力注册表中的逻辑能力，声明输入输出、资源、网络、文件和沙箱级别。不得上传任意安装脚本、凭据、二进制或自更新器。夹具在无秘密、无生产网络的沙箱运行。

### 6.4 夹具构建

模板强制包含问题类型、输入快照、预期 Claim、来源版本、触发规则、预期状态、允许/禁止措辞、人工门和理由。覆盖面板分别显示正例、反例、边界、版本变化、冲突、恶意和人工门，不以总数量掩盖缺失类别。

### 6.5 语义 Diff

默认只显示有判定意义的变化：

- Claim Schema、证据映射和措辞强度；
- `BLOCKED`/`CONFLICTED` 变为可发布；
- 人工门降低或升高；
- 来源权威范围与过期预算；
- 依赖和逻辑能力；
- 夹具新增、删除、翻转和不稳定；
- 旧产物将进入 stale、重跑或迁移。

原始文本/YAML Diff 作为二级视图，不能替代语义 Diff。

### 6.6 资质与利益冲突

签名前展示：

- 当前角色需要的资质范围；
- 已核验记录、核验人、有效期和覆盖学科；
- 本版本利益冲突问卷及与来源/作者/资助方的关联；
- 是否允许参与、只能提供意见或必须更换复核者。

重大未披露冲突触发签名撤销、影响分析和重新复核。界面不公开身份证件，只公开足够的资质类别和冲突摘要。

### 6.7 双签与发行仪式

每次签名弹窗展示相同不可变摘要：

- Manifest、内容树、依赖锁、夹具和构建出处摘要；
- 语义 Diff 和下游影响；
- 未解决意见和风险；
- 签名角色、资质、利益冲突版本；
- 签名后任何修改都会失效。

按钮分别叫“提交内容签名”“提交独立验证”“追加发行签名”，永远不使用通用“批准并发布”。

### 6.8 灰度验证

发行候选先执行：

- 全量确定性夹具和依赖闭包；
- 跨包组合、迁移和旧/新双跑；
- 影子运行，不影响真实产物；
- 指定项目的受控灰度；
- 科学、安全、时延和资源指标；
- 失败样本与受损切片。

灰度结果只生成 `READY_TO_RELEASE` 候选，不自动激活。平台发行者必须再次确认签名与门仍有效。

### 6.9 正式发行

平台发行者只能执行不可编辑的发行命令。系统重新计算摘要、签名、资质、冲突、依赖、撤销、过期和灰度门；任何变化都回到相应阶段。发行后生成透明记录、安装策略、默认范围、取代关系和重验证时间。

### 6.10 失效、紧急撤销和回滚

失效事件页面按影响带展示：

`触发源 → 包/规则 → 运行 → Claim/Evidence → Wording/产物 → 项目/用户动作`

- 来源未知或重大争议：暂停高置信发布；
- 签名无效、恶意依赖、跨租户或 H3 风险：立即撤销并阻止新运行；
- 非实质勘误：计划更新；
- 历史产物始终保留原快照和当时状态。

紧急撤销要求二次认证、输入包 ID/版本、选择原因、确认影响范围，并产生不可修改事件。安全管理员不能在同一操作里上传修复包或激活旧版。

回滚只允许选择仍有效、依赖兼容且通过当前平台下限的旧版；先做影响与迁移检查，再由独立复核者和平台发行者确认。被撤销版本不能通过“回滚”重新激活。

## 7. 异常与拒绝流程

| 场景 | 系统裁决 |
|---|---|
| 同一人尝试内容签名与独立验证 | 拒绝并记录职责冲突 |
| 复核者资质不覆盖包范围或已过期 | 阻止签名，要求重新核验或更换复核者 |
| 复核者与关键来源有直接利益关系且是唯一复核人 | 阻止发行，可保留其专家意见 |
| 未声明利益冲突 | 阻止签名 |
| 规则试图放宽平台权限、安全、租户隔离或 H3 下限 | 永久拒绝该变更，不提供 override |
| 缺反例、恶意例或人工门夹具 | 阻止进入独立复核 |
| major 版本无迁移、双版本对照或回滚窗口 | 阻止提交发行候选 |
| 来源状态接口失败 | 按策略进入 unknown/暂停，不能假定 active |
| 依赖环、路径穿越、未声明二进制或安装脚本 | 隔离并创建安全事件 |
| 签名摘要与当前内容不一致 | 全部旧签名失效，返回编写阶段 |
| 独立复核者拒绝 | 进入 `CHANGES_REQUESTED` 工作阶段；不能由发行者覆盖 |
| 专家意见影响安全等级或措辞强度 | 暂停并保留少数意见 |
| 灰度发生硬门失败或关键回归 | 闭锁发行候选 |
| 发布按钮重复点击/网络重试 | 同一幂等键只产生一个发行事件 |
| 签名服务不可用 | 保持已验证旧版，不降级为无签名发布 |
| 安全管理员撤销后想直接激活旧版 | 拒绝，必须走兼容性、复核和发行链 |

## 8. 三套原型

### A：阶段控制台（推荐主框架）

- 左侧是八阶段发行轨道；
- 中部围绕当前阶段显示任务、Diff 和门；
- 右侧固定显示来源、签名、资质、利益冲突与平台下限；
- 最适合把“下一步由谁负责”说清楚。

### B：证据与 Diff 工作台

- 左侧是包对象树；
- 中部是旧版/新版与判定差异双栏；
- 底部是夹具翻转和下游影响；
- 最适合深度复核，但单独使用时不如 A 清楚地表达流程责任。

### C：责任泳道与失效指挥台

- 维护者、复核者、发行者、安全管理员四条责任泳道；
- 顶部显示风险、签名和失效影响；
- 中部按角色展示等待项与禁止动作；
- 最适合发行日和事故处置，但日常规则编辑效率不如 B。

原型入口见 [领域包专家工作台 UI 原型](../prototypes/domain-pack-expert-workbench/README.md)。

## 9. 验收标准

1. 同一人不能对同一摘要完成内容签名与独立验证；
2. 平台发行者不能编辑规则或绕过独立复核；
3. 安全管理员能立即撤销，但不能发布；
4. H3 必须联合签名且任一依赖服务失败即闭锁；
5. 每条规则能追到来源、定位、夹具、复核和发行签名；
6. 语义 Diff 能识别人工门下降、措辞增强和 `BLOCKED` 翻转；
7. 依赖影响能定位下游包、运行、Claim 和产物；
8. 资质、利益冲突和少数意见均逐版本保存；
9. 灰度不会自动激活，正式发行前再次校验全部门；
10. 撤销阻止新运行，但旧运行仍可按原快照审计；
11. 回滚不能复活已撤销或不兼容版本；
12. 任何按钮、重试、override 或领域包文件都不能放宽平台下限；
13. 所有关键状态同时使用文字、图标和颜色；
14. 键盘、屏幕阅读器、缩放和减少动画可以完成复核与签名；
15. 普通用户公开视图不泄露专家证件或不必要利益信息。

## 10. 确认结果

用户于 2026-07-24 确认采用：

> **A 作为工作台主结构 + B 的语义 Diff 主画布 + C 的责任泳道和失效影响带。**

本文件据此成为正式决策。原型中的具体 CSS、静态数据、模拟按钮和底部方案切换器不进入生产实现。
