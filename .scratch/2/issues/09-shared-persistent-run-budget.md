# 09 — 持久化整次运行预算与有限调整额度

**What to build:** 同次运行的节点、并行、重试和恢复共享截止时间与调用额度；预算耗尽时交付已核实部分或明确阻塞。

**Blocked by:** 03 — 锁定完整模型额度与每次调用版本；08 — 保存有来源的跨轮任务、有效条件与澄清

**Status:** ready-for-human

**优先级：** P0

## 任务内容

1. 运行创建时冻结截止时间、调用/token 上限、已耗额度与核验/交付预留；计数持久化并由内核唯一修改，模型不能延时或扩容。
2. 按已确认初值方案试行：普通检索 60 秒、深入/书页最多 120 秒；核验交付先预留 15/30 秒；外部独立并行初期最多 2，初筛 20、普通重点深读 3、深入 5。作为待校准初值，不宣称性能承诺。
3. 整次运行最多一轮自动补证/调整，结构和内容修复共用此轮；每个登记的临时传输失败最多重试 1 次，检查错误类型、冷却和剩余额度。
4. 配方从必要节点、候选读取上限和有限修复计算调用数/token 上限。明确深入需求在创建时获更高预算，不由主智能体临时无限增加。
5. 恢复保留原截止和消耗；用户明确继续/修改建立新运行、复用有效产物。限流等待超过剩余预算就结束，有真实恢复时刻才按 Asia/Shanghai 显示。
6. 普通轻量交流沿用已验证超时；摘要、提取后台任务各有独立有界运行，调用目的分别计量。先贯通普通调用的停止/重试/恢复，10 贯通首个确定性模块。

7. 在共同上下文边界给出可核验分批计划时，执行登记的有界分批，冻结批次数/耗时和中间来源引用；不能保持原任务含义时返回受限结果，不自动缩小任务。

### Standards

- 修正兼容补建审计流水脱离事务、冻结竞争可能发生唯一键错误、关闭/耗尽读取快照与提交分离的问题。账本组合操作持连接锁并入外层事务，守门、版本更新和流水在同一事务完成。
- 原网关以能力名作为调用标识，导致同能力的不同调用共用重试额度。现每次网关调用生成独立标识，本调用的重试与结果复用该标识。
- 原结果只更新累计 token，没有填写逐调用流水的 token 字段。现输入、输出、用途全部落流水；重复结果幂等，耗尽/关闭后的真实迟到计量仍可补记。
- 原外呼重复释放会误减其他调用占位。现按调用标识检查未释放登记；并行搜索只在 Future 真正结束或成功取消后释放。单实例数据目录锁保证进程更替时旧进程已退出，恢复只回收旧进程占位，保留同进程仍在执行的占位及历史调用消耗。

### Spec

- 增加持久仓库对冻结工作截止（总截止减核验交付预留）、未知预算合同版本、运行停止/终态的守门。供应商入口在冷却后重新检查，单次与账户级停止立即关闭账本；每次实际传输重试也计入运行调用上限。
- 现有职业规划结构修复领取共享的一轮自动调整，并登记调整结果；已用过调整轮时不发起第二轮。具体多节点调整计划由 10/12/37 消费同一接缝。
- 补齐执行器已提交消息恢复、已有终态队列遗留、排队停止等提前返回路径的关账本；会话与运维运行删除同时清理账本/流水。
- 补齐任务 4：不可变 `RunBudgetRecipeCosts` 按必要调用、候选读取和一轮修复计算调用上限，并计入至多一次传输重试与输入/输出 token 上限；成本依据和配方版本随冻结计划持久化。现有普通调用仍保留明确标注的初值，后续实际配方可提供代码计算成本，模型不能临时增加额度。
- 补齐任务 7：`BoundedBatchPlan`、`BudgetBatch`、`BatchSourceRef` 和 `BoundedBatchExecutor` 接收共同上下文边界明确登记的有限计划，核对原任务指纹和必需来源覆盖；冻结批次数、耗时、调用/token 上界及来源版本/读取范围。顺序执行使用同一账本，每批结束保存完成引用；恢复跳过完成批，未完成批沿用首次截止和已耗计数，不能领取全新批次额度。停止、超时、计划改写、缺少覆盖及超预算计划均明确拒绝，不自动缩小原任务。
