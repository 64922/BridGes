## 推荐安排：三个实施执行者

| 执行者 | 首个任务 | 后续任务 | 选择原因 |
| --- | --- | --- | --- |
| A | 01 画像恢复 | 03 通勤解析 | 先处理数据风险；后续工作主要在独立解析模块 |
| B | 02 设置入口 | 06 贴吧搜集 | 先恢复用户可操作入口，再修复独立模块 |
| C | 04 学习识别 | 05 GitHub 推荐 | 尽早核验仍有证据缺口的图片请求，再处理推荐 |

三个执行者可同时开始第一张票，完成后立即领取本线路后续票，不必等待其他线路。第二阶段分配只是工作量建议，不是新的硬依赖：任何空闲执行者都可领取无人认领且依赖已解除的工单。01—06 都可独立开发，条件允许也可以使用更多执行者；不建议为了同时运行而让所有执行者共享同一个可写目录或真实数据目录。

六张修复票都集成后，由一个指定执行者统一执行 07。07 中的静态清单准备可提前进行，但真实升级与最终结论必须等待全部依赖完成。此建议不意味着本次已经启动子智能体或创建新任务。

## 开发依赖与验收前提

- 03 的解析与服务测试不依赖 02，可以独立完成；从聊天界面配置密钥再查询真实路线的完整操作链，在 07 中等待 02、03 一起就绪。
- 04 使用当前有效模型配置与独立测试数据即可开发，不以新设置入口为硬依赖；需要更换凭据时使用 02 的真实界面验收。
- 01 必须使用独立数据库副本，不得在其他执行者测试过程中升级共享真实库。
- 05 的公开 GitHub 调用和 06 的搜索调用不互为依赖，但应避免集中做高频真实调用。外部额度耗尽时完成可确定验证的部分，并记录真实验收缺口。

## 冲突与集成规则

1. 每张票使用独立工作树和 `codex/` 前缀分支，Python 统一使用 `agent` 环境；分配独立数据库、对象目录和开发服务端口。测试数据不得覆盖用户原始材料。
2. 数据库迁移编号与结构合同由 01 负责；其他票若确需迁移，先由集成负责人协调分配，不得并行占用同一版本号。实际提交时依据最新主分支分配新版本，不将计划中的“下一版”硬编码成旧值。
3. 02 负责共享侧边栏、账户菜单和通勤卡片中的配置链接；03 优先只改通勤解析及服务测试。如需同时调整通勤卡片，先协调修改范围。
4. 04 负责共享 OCR／视觉请求构造和模型探测。05、06 不修改模型网关。不要把这两个模块的中文问题顺手抽象成全仓库共用分词器。
5. GitHub 与贴吧的结果卡片、模块测试分别归 05、06；若必须修改共享结果类型或应用装配，先约定接口，再由一个执行者提交共享部分。
6. 每次合入完成必要的定点回归；所有修复合入后只做一次完整联合验收。合并冲突不得以“取某一侧全部代码”替代语义检查。

## 完成记录

每张票的“执行与验收记录”填写提交版本、实际复现命令、失败和成功输出、测试范围、真实调用结果、尚未解决项。分诊状态沿用仓库五种标准状态，不自行发明完成标签；是否完成以验收勾选和完成记录判定。未完成真实验证的项目保持未勾选，并在 07 中汇总。
