# Issue 12：冻结 holdout 并完成发布验收

Status: ready-for-agent

Type: task

Priority: P0

Parent: [BridGes 有人味表达改进方案](../README.md)

User stories: US-01、US-02、US-03、US-04、US-05、US-06、US-07

## What to build

在文章、聊天、结果投影和正式评测门全部完成后，解封一次冻结 holdout，使用同一运行锁对 current production、candidate、plain model 和 `Humanizer-zh` reference 执行真实配对运行，完成保真硬门、至少三个隔离系统裁判的自动盲评、配对统计、成本/延迟分析、消融和回滚演练，给出可发布、不可发布或证据不足的最终结论。

本 Issue 是发布验收，不是继续调 prompt 的开发任务。任何失败案例先归档和分类；若需要改实现，必须创建新候选版本和新评测运行，并将当前 holdout 标为已使用，不能只修失败项后声称仍是盲测。

## 已验证现状与根因摘要

- 当前人味发布门不存在，工程测试通过不能阻止自然度严重退化。
- 现有 scripted 输出和弱短语指标无法回答新版是否优于当前或与 `Humanizer-zh` 基本持平。
- 用户要求最终效果不落后太多，同时已经确认保真、分寸和不编经历比追求单篇 9.5 分更高优先级。
- 文章定向修订增加了潜在成本和延迟；普通聊天必须验证仍为一次调用。
- 方案含多个机制，需要消融才能区分改善来自来源账本、任务契约、正向生成、审稿、第二次修订还是评测偏差。

## 非目标

- 不在看过 holdout 输出后直接修改该运行的规则或裁判。
- 不挑选有利案例、删除失败运行或只报告总体均分。
- 不把一次在线探针成功解释为长期模型稳定性。
- 不接入人工评分、抽查、仲裁或发布签核，也不在未通过门禁时用主观感觉强行放行。
- 不删除 current 策略或无法恢复的生产配置。

## Acceptance criteria

- [ ] 开始前验证 Issue 05、06、07、08、11 全部完成，预注册配置、candidate build、策略、语料、holdout、参考 SKILL、模型参数和匿名种子均已冻结并记录哈希。
- [ ] holdout 解封有一次性审计事件；原始输出按 Issue 09 append-only 保存，失败、超时和重试均保留，不进行逐案重写、人工挑选或人工覆盖裁决。
- [ ] current、candidate、plain model 和 `Humanizer-zh` reference 使用可比输入与参数配对运行；无法相同的系统边界、模型或可重放性限制在报告开头明确披露。
- [ ] 每个输出先运行来源保真硬门；关键事实、保护区、虚构亲历或检查缺失导致对应 surface 发布失败，不把违规稿送入只看自然度的结论。
- [ ] 每个正式比较项至少由三个合格系统裁判完成双向匿名评价；候选映射没有泄漏，模型多样性、canary 校准、漂移和顺序一致性达到 Issue 10/11 的预注册要求。
- [ ] candidate 相对 current 的聊天与文章分别达到 95% CI 下界 >50%；文章相对 `Humanizer-zh` 达到下界 ≥45%；任何未达到项均不得描述为“基本持平”。
- [ ] 关键保真严重失败为 0，非关键保真通过率 ≥99%；do-no-harm 切片中原文已自然案例没有系统性被加场景、亲历、金句、总结或亲密称呼。
- [ ] 按模式、文章强度、体裁、长度、风险和失败模式报告；普通聊天一次模型调用率为 100%，文章第二次修订只在触发条件满足时发生且总调用不超过 2。
- [ ] 报告 current/candidate 的 p50/p95 延迟、token、成本、文章修订触发率和问题解决率；实际预算不超过 ADR/运行锁，超预算案例单独失败。
- [ ] 至少完成以下消融：无来源新增检查、无表达审稿、无第二次修订、旧聊天全量规则、plain model；消融只用 development 或预注册 holdout 子设计，不能事后选择有利组合。
- [ ] 失败案例按来源、契约、生成模型、保真、审稿、修订、投影、系统裁判和外部参考分类，记录稳定 case ID、输出哈希、责任模块和建议后续 Issue，不在摘要复制正文。
- [ ] 在预发布环境演练文章修订开关、聊天策略版本和结果投影回滚；回滚后 current 行为、历史任务读取、保护区和来源硬门状态符合文档。
- [ ] 无人值守发布裁决只允许 `pass`、`fail` 或 `inconclusive`：只有全部独立门通过才为 `pass`；任何系统裁判或检查异常不得由人工改成通过。
- [ ] 发布报告明确写明结果仅代表冻结自动裁判体系，`human_validated=false`；不得声称真实中文用户已经验证与 `Humanizer-zh` 持平。

## Test plan

1. 在解封前运行全部 schema、合同、来源、文章、聊天、盲评、统计、API、Web 和迁移回归，保存代码与环境哈希。
2. 对 holdout 执行一次完整真实运行；验证 SUT 对齐、append-only、调用计数、超时/停止、匿名包和 sealed mapping。
3. 完成至少三个隔离系统裁判的双向盲评、canary 校准、漂移检查和自动一致性裁决，生成聊天和文章独立统计报告；任何阶段不等待人工输入。
4. 运行预注册消融并生成差异表，验证关键改善不是词表或候选身份泄漏造成。
5. 模拟文章二次修订提供方失败、策略回滚、前端投影回滚和旧结果读取；验证不交付硬门失败正文。
6. 对高风险、材料不足、不伤害、长文、学习模式短答和用户失败型文章运行确定性 oracle、来源绑定验证和系统裁判证据 span 校验，机器确认报告引用与实际输出一致。
7. 用版本化策略自动校验许可证/净室清单、成本预算、已知限制和回滚探针；任何未知或无法机器确认的项产生 `inconclusive`，不转交人工签署。

## Observability & rollback

- 发布证据包含 build、运行锁、语料/holdout/策略/SKILL/系统裁判哈希、门禁、CI、自动盲评、统计、延迟、成本、失败分类和回滚结果，不含密钥、账户 ID 或私人正文。
- 发布后观察聊天长度/下一问率、文章修订触发率、保真阻断、`needs_user_confirmation`、p95 延迟、成本和用户反馈分层；不得用单一点赞率代替冻结门。
- 回滚顺序：先关闭文章定向修订，再恢复聊天/文章上一策略版本，再恢复旧结果投影；任何回滚都保留来源硬门、审计和历史输出。
- 任一 P0 门失败时维持 current production，候选版本不进入默认流量；新一轮修复创建新 Issue、candidate 和评测运行。
