# Issue 04：重建文章首稿与表达审稿器

Status: ready-for-agent

Type: task

Priority: P0

Parent: [BridGes 有人味表达改进方案](../README.md)

User stories: US-02、US-03、US-05

## What to build

以表达任务契约和来源账本为唯一上游输入，重建文章首稿生成与生成后表达审稿。首稿只接收当前场景真正相关的少量正向规则，围绕说话位置、材料和读者下一问推进；不再把完整方法 ID、黑名单和体裁必现短语同时塞入模型。生成后，独立表达审稿器对候选正文定位模板动作、PPT 式抽象包装、假具体、假口语、强行场景、节奏单一和无必要升华，并输出可供 Issue 05 定向修订的报告。

这条切片结束时，现有文章入口仍能完整交付结果，但科普、讲稿、科研汇报和论文辅助不再为了通过正则检查强行加入定义、类比、练习、局限或下一步。保真硬门由 Issue 02 提供；表达审稿默认只报警，不做机械词语替换。

## 已验证现状与根因摘要

- 当前 `genre_rules.py` 通过必现正则判断科普定义、类比、边界提醒、讲稿目标/检查/练习、科研方法/局限/下一步等，直接制造可预测结构。
- 当前 `method_rules.py` 把大量带 ID 和标签的规则渲染进提示；普通业务抽象词和“以概念解释概念”的 PPT 腔却没有被可靠识别。
- 当前结构化调用同时要求正文、修改明细、事实核查和开放问题，模型需要一边创作一边生产审稿元数据。
- 现有规则一致性测试要求所有方法标签进入文档和提示，证明规则装配一致，但也固化了超长总提示。
- `human-writing` 的有效启发是先确定说话位置和材料推进，再在初稿后审稿；其标点硬禁令和论坛长帖声音不适合作为全局规则。

## 非目标

- 不在本 Issue 中增加第二次模型调用。
- 不把词表命中直接等同于“AI 生成”或对用户显示 AI 检测结论。
- 不全局禁止冒号、破折号、三项列举、设问、第一人称、比喻或总结。
- 不自动替换精确引语、代码、公式、URL、合法术语和用户指定措辞。
- 不复制三个参考项目的提示、示例、规则文字或代码结构。

## Acceptance criteria

- [ ] 文章执行器只从版本化表达任务契约和来源账本取得任务、权限和材料；未提供或版本不支持时在模型调用前稳定拒绝。
- [ ] 为轻度、标准、深度定义原创正向生成 profile：轻度尽量保留词汇、段落和作者声音；标准允许调整段落推进与句式顺序；深度允许重构组织和叙述，但三者共享来源硬门与不伤害原则。
- [ ] 每次首稿只编译当前 profile 的 6—10 条高优先级规则；生成提示不包含内部方法 ID、全量检测清单或为了审计而写给模型的冗长标签。
- [ ] 首稿明确携带说话位置、读者下一问、材料边界和第一人称/假设权限；无权限时不得要求模型加入生活场景或亲历。
- [ ] 体裁 profile 只规定任务目标、风险和可选表达方式；删除“必须出现定义短语/类比/练习停顿/局限/下一步”等正则完成条件。未声明体裁使用通用文章 profile。
- [ ] 模型生成合同以候选正文为中心；修改清单、保真结果、模式命中和可确定性差异由程序生成。若为授权外部材料生成 claim，可返回最小来源绑定，不要求模型撰写自评文章。
- [ ] 定义版本化 `ExpressionReviewReport`，每条发现包含稳定 code、场景 profile、严重度、文本起止位置、命中证据、解释和定向修改建议。
- [ ] 审稿至少覆盖：助手身份残留、机械承接/收尾、体裁脚手架、抽象名词链、商业/PPT 隐喻、用术语解释术语、同义循环、空段、重复开场、句长/段长过齐、密集排比或设问、假具体、无权限第一人称、强行生活场景、每段金句和通用乐观升华。
- [ ] 审稿按场景解释词语：专业原义、原文已有表达、精确引语和 protected spans 跳过；单个词语、冒号或破折号不得独立造成硬失败。
- [ ] 来源保真问题继续由 Issue 02 硬门裁决；风格发现默认为软审稿。自然稿无高价值修改时报告 `no_change_recommended`，系统不得为满足规则强行改写。
- [ ] 旧 API/事件/结果投影在 Issue 08 前保持兼容；无法从模型直接取得的修改与核查字段由确定性适配器生成，不向用户伪装成模型自证。
- [ ] 更新净室记录，说明只吸收材料门槛、说话位置、先写后审等通用思想，新增规则、夹具和实现均为 BridGes 原创。

## Test plan

1. 对每个 profile 做提示快照测试，断言只包含当前相关规则且不再包含全量方法 ID 或旧体裁必现短语。
2. 为用户失败型时间管理文章建立回归：不得新增亲历；不得把“颗粒度、带宽、释放内存、元认知”等抽象包装换一套说法继续保留；应能把至少一个抽象主张落到源文已有动作。
3. 用原文已自然、精确引语含黑话、合法技术术语、必要三项清单和含冒号定义的样例验证不伤害与误报白名单。
4. 用科普、讲稿、科研汇报和论文正文验证不再为了合同凭空添加类比、练习、方法、局限、下一步或元建议。
5. 用强行第一人称、装饰性深夜/咖啡/雨、每段金句、机械三段式、商业隐喻链构造审稿器表驱动测试，验证位置和 code 稳定。
6. 使用假模型跑完整文章服务，验证首稿、保真硬门、审稿报告、旧投影和错误状态；本 Issue 中模型调用始终至多一次。
7. 在显式开发探针中对当前与候选各跑一组原创 development cases，保存原始输出和结构化机器诊断，但不把这组结果作为最终发布结论。

## Observability & rollback

- 记录 profile/强度、编译规则数量、首稿延迟与 token、各审稿 code 数量、`no_change_recommended` 比例、保真硬失败和软警告；不记录私人正文。
- 分体裁和长度观察高频告警及误报，不用单一总分隐藏某个 profile 的退化。
- 以文章策略版本灰度；回滚恢复旧提示与体裁合同，但保留新报告只读记录。来源硬门不得因风格回滚被关闭。
