# Issue 01：跑通真实人味评测 tracer bullet

Status: ready-for-agent

Type: task

Priority: P0

Parent: [BridGes 有人味表达改进方案](../README.md)

User stories: US-01、US-02、US-06、US-07

## What to build

建立一条最短但真实的端到端评测链路：选取一个“抽象时间管理文章、原文没有个人经历”的文章案例和一个“简单问题不应扩成教学长文”的聊天案例，使用真实生产模型适配器分别运行冻结的当前 BridGes、候选配置和挂载指定 `Humanizer-zh` 快照的参考配置，保存不可变原始输出，执行最小保真检查，并导出不泄漏候选来源的系统裁判包。

本 Issue 的目的不是证明新版已经优秀，而是尽早证明“真实输入 → 真实模型 → 三方输出 → 保真结果 → 匿名系统裁判包 → 可重放证据”整条链路存在。候选尚未改进时允许与当前输出相同，质量结论必须标记为 `inconclusive`，不能用脚本答案或 no-op reference 冒充基线。

## 已验证现状与根因摘要

- 现有 `natural_language_eval.md` 有 30 个原创案例，但测试只验证 ID 和栏目，没有调用真实模型。
- 内置 humanization suite 只含少量脚本答案；执行器直接返回案例中的预写输出，seed 变化不能证明模型稳定性。
- 当前 reference SUT 在人味任务上基本返回 source，不是 `Humanizer-zh`。
- 现有 blind review 对象只带两段输出，缺少原文、任务合同和事实锁，且 `item_id` 与标签字段可能泄漏比较映射。
- 用户反馈的失败集中于商业/PPT 抽象词、理论化包装、缺少真实说话位置；文章案例必须覆盖这些症状，同时禁止用“我以前、上周朋友、半小时前、刷短视频”等无来源经历刷自然度。

## 非目标

- 不在本 Issue 中重写文章或聊天生产策略。
- 不建立完整 120 案例语料、统计显著性或发布门。
- 不使用生成候选的同一次模型会话给自己评分，也不把单个模型自评分当作可靠结论。
- 不采集真实用户私人正文、账户标识或未获授权的生产消息。
- 不把 `scientific-humanization` 的文字、结构或示例复制进夹具。

## Acceptance criteria

- [ ] 增加一个版本化的 article case 和一个 chat case；每个 case 包含用户请求、原文或上下文、表面类型、模式、受众、渠道、长度、允许材料、禁止新增 claim、保护项、许可证/来源说明和内容哈希。
- [ ] 文章 case 明确记录“原文没有个人亲历”，并把新增作者亲历、朋友对话、具体时间地点、未经来源支持的数据或功能判为严重失败。
- [ ] 三个 SUT 身份真实且不混淆：冻结的 current production、当前代码 candidate、指定 `Humanizer-zh` SKILL 快照；参考快照记录绝对来源、内容哈希、许可证状态、基础模型和参数。
- [ ] 真实运行通过生产模型调用适配器产生输出，不使用案例内脚本答案；缺少凭据或参考快照时运行结果为 `inconclusive` 并明确列出缺项，绝不回退为假成功。
- [ ] 每次运行记录代码/build、SUT、策略/SKILL 哈希、模型快照、temperature、top_p、seed、重试、开始结束时间和 case 哈希；原始输出 append-only，重放不会覆盖旧记录。
- [ ] 最小保真检查至少覆盖数字、单位、日期、专名、精确引语、URL、否定词和第一人称经历新增；检查缺失时 case 不得标记通过。
- [ ] 导出 judge-facing packet 时只出现不透明 item ID、固定显示标签 A/B、用户请求、原文、任务边界、保护项和候选正文；不得出现 SUT、peer ID、策略名、模型身份或内部映射。
- [ ] organizer-only mapping 与 judge packet 分开保存；使用相同匿名种子可重现映射，改变种子会改变左右顺序。
- [ ] 至少接入三个隔离的系统裁判适配器，并确保裁判调用不继承候选生成会话、隐藏状态、工具记录或候选来源；只有一个裁判可用时结论固定为 `inconclusive`。
- [ ] 每个裁判对同一配对执行 A/B 与 B/A 双向判断，返回结构化偏好、七维评分、证据 span 和无法判断原因；位置翻转导致不一致时记录无效裁决。
- [ ] 提供一个可复制命令完成案例校验、真实运行、保真检查、系统裁判调用和裁判包导出，并生成不含私人正文的执行摘要。
- [ ] 样本只有两个 case、系统裁判不足/不合格、顺序一致性失败或任一运行锁不完整时，报告结论固定为 `inconclusive`。

## Test plan

1. 用假模型适配器做确定性集成测试，验证三个 SUT 都经过同一执行协议，脚本化 executor 不可被误选。
2. 用临时输出目录连续运行两次，验证 append-only、内容哈希、重放和不覆盖语义。
3. 构造包含“我以前”“上周和朋友聊”“半小时前”“5000 例”的候选输出，验证文章 case 的最小保真检查跑红。
4. 扫描 judge-facing JSON/Markdown 的全部字段和值，断言不包含 SUT 名、peer ID、策略版本、生成模型身份、内部标签或映射键。
5. 使用三个假裁判验证隔离调用、双向顺序、结构化输出、分歧和 `inconclusive`；不得出现任何等待人工输入的状态。
6. 在显式允许真实提供方的开发环境运行一次三方生成与多裁判 smoke；保存脱敏运行摘要和机器可重放的裁判包。

## Observability & rollback

- 记录各 SUT 与裁判调用次数、成功/失败、模型延迟、token、重试、保真失败类型、裁判分歧和裁判包数量，不把原文或输出正文写入普通日志。
- 真实提供方运行必须显式启用；普通 CI 只运行协议与匿名化测试。
- 新链路独立于生产发布门；回滚只需关闭开发评测入口并保留已经生成的 append-only 证据。
