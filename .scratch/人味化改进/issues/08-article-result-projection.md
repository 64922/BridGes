# Issue 08：实现正文优先的文章交付界面

Status: ready-for-agent

Type: task

Priority: P1

Parent: [BridGes 有人味表达改进方案](../README.md)

User stories: US-02、US-04、US-05

## What to build

把文章人味化的 API 投影和聊天内展示调整为“正文优先、审计按需展开”。首屏直接呈现可复制的最终正文，不附固定自夸、方法说明或冗长事实核查总结；修改摘要、来源保真、表达审稿、证据风险和定向修订记录进入可访问的折叠区域。只有材料不足、硬门失败、证据降级或待用户确认时，风险才在正文前得到明确但克制的突出显示。

模型不再负责生成大量面向 UI 的审稿文字。修改范围、检查结果、前后差异和风险项应优先由 Issue 02、04、05、06 的结构化记录确定性投影，避免审计面板本身继续使用模板腔。

## 已验证现状与根因摘要

- 当前领域合同固定输出最终文本、修改明细与理由、事实核查和未解决问题；模型在一次调用中同时撰写这些字段，分散正文生成注意力。
- 普通无风险文章也会得到结构完整但信息价值低的审稿元数据，产品表面显得像质量报告而不是写作工具。
- 事实硬门、软审稿、证据风险和用户可发布正文目前没有足够清晰的视觉与协议层级。
- 用户已经确认首屏正文优先，审计按需展开；发生风险时才突出，并保留用户主动查看逐项对照的能力。

## 非目标

- 不在 UI 中重新计算事实或风格结论。
- 不隐藏硬门失败、证据降级、材料不足或待用户确认。
- 不删除审计记录或让折叠等同于不保存。
- 不改变普通聊天消息的整体布局。
- 不用模型生成的“我做了哪些改进”替代确定性差异。

## Acceptance criteria

- [ ] 定义版本化文章结果投影，至少区分 final text、delivery status、material state、fidelity summary、style review summary、targeted revision summary、evidence risk/change、user confirmations 和审计版本。
- [ ] 成功且无风险时，聊天消息首屏以最终正文为主；不自动显示“已完成人味化”“主要修改如下”等固定前言或空事实核查段。
- [ ] 修改、来源保真和审稿信息放入有清晰计数与状态的可展开区域；键盘、屏幕阅读器和移动端可访问，折叠状态不影响复制正文。
- [ ] 硬门失败时不把违规候选标为最终正文；界面显示稳定失败原因和可采取的下一步，正文区域明确区分“未交付候选”或不显示违规稿。
- [ ] 材料不足时只显示一个最高价值问题，或按契约展示短稿/占位符；不得同时堆叠多个通用建议。
- [ ] 证据安全修订产生实质 claim 变化时，在风险区域展示原文片段、改后片段、原因、来源和需确认状态；默认普通人味化只展示风险，不伪装成已经修正。
- [ ] 第二次定向修订发生时显示“为何触发、解决了哪些问题、仍有哪些风险”，但不展示内部提示词、模型思维链或完整规则清单。
- [ ] 修改明细优先来自确定性 diff 和结构化报告；模型返回的自由文本不得作为唯一依据。没有可定位证据的泛化理由不展示。
- [ ] 用户可以主动展开完整逐项对照并复制；审计内容包含版本和稳定 code，避免把私人正文写入前端遥测。
- [ ] 旧文章结果仍可兼容读取；旧字段以明确的 legacy 投影展示，不伪造新来源硬门或新审稿通过状态。

## Test plan

1. 为成功无风险、软警告、材料不足、硬门失败、证据风险、证据安全修订和二次修订建立 API 投影契约测试。
2. 组件测试验证正文首屏、审计折叠、计数、复制、键盘与屏幕阅读器名称。
3. E2E 通过真实本地 API 跑至少一个无风险改写和一个证据变化任务，验证流式过程、终态、刷新恢复和旧结果读取。
4. 用窄屏、长文、长引语和多个风险项验证正文可读、折叠不溢出、复制内容不混入审计文案。
5. 断言普通无风险结果没有固定事实核查总结或自夸前言；硬失败绝不显示为可发布最终稿。
6. 运行聊天消息、历史恢复、停止/重试和文章路由相关 Web/Python 回归。

## Observability & rollback

- 只记录投影版本、状态、风险类型、展开率、复制事件和 legacy 读取数；不记录正文、引语或逐项 diff 内容。
- 观察硬门失败被错误投影为成功、审计缺失、复制混入元数据和旧结果读取错误，任何一项均阻止发布。
- 以 API 投影版本与前端能力开关灰度。回滚恢复旧展示但保留新结构化记录；不得通过 UI 回滚隐藏后端硬门失败。
