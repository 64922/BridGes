# Issue 08：安全升级 profile-auto-v2 并回放存量画像

Status: resolved
Type: task
Priority: P0
User stories: US-03, US-04, US-05

## What to build

在 Issue 06 的统一分类与 Issue 07 的可用网关合同完成后，交付 profile-auto-v2 的安全升级和存量回放纵向路径：识别运行时权威数据库，执行显式 schema 门与可恢复备份，先 dry-run 生成脱敏影响报告，再按账户幂等回放历史 exhausted 失败与 succeeded/attempts=0 静默跳过运行，由受监督 worker 收敛，最后通过画像 API、页面和审计报告验证结果。

运行工具不得默认假设仓库根目录的 bridges.db 就是应用正在使用的数据库。它必须从统一运行配置或应用状态解析权威数据库，输出规范化位置和数据库身份摘要供操作者确认；路径冲突、进程仍在写入、schema 未达到目标版本、备份不可恢复或配置来源不明确时必须停止。

升级抽取器版本为 profile-auto-v2，使新分类语义拥有新的幂等边界。保留 v1 运行作为审计事实，不原位伪装为 v2 成功；v2 回放必须重新读取当前有效消息，并遵守账户隔离、消息墓碑、停止记录、内容级隐私阻止和画像撤回屏障。

## 已验证复现与根因摘要

- 只读样本数据库仍处于 schema 42，而当前程序支持 schema 43；直接运行现有重排队脚本会调用数据库初始化并发生隐式升级，与脚本说明的“不静默迁移”承诺不一致。
- 样本库有七条 profile-auto-v1 运行：三条 exhausted/attempts=3/client_error_400，四条 succeeded/attempts=0；全库 observation 和四维记录均为零。
- succeeded/attempts=0 代表预检跳过，但被建模成 succeeded。现有清理脚本只筛选 client_error_400，不会回放这些静默漏抽取。
- 当前抽取器版本未随分类和网关修复变化；同版本 succeeded、pending 或 exhausted 运行会被幂等短路，因此仅部署代码不能修复存量账户。
- 对用户已提供主题进行脱敏聚合后，静默成功和 400 两组中都命中了人工智能、考研、Transformer 或论文信号，具备回放价值。

## 非目标

- 不在本任务中重新定义画像分类语义或供应商错误合同；必须复用 Issue 06、Issue 07 已验收实现。
- 不删除、覆盖或改写 v1 运行、历史消息、迁移审计和用户有效证据。
- 不回放已删除、已墓碑、已被账户/内容隐私边界阻止的消息，不复活已撤回画像。
- 不把 dry-run 设计成隐式写入、schema 初始化、队列创建或锁状态变更。
- 不在未识别权威数据库或未验证备份时对任何候选数据库执行修复。

## Acceptance criteria

- [ ] 自动画像抽取版本升级为 profile-auto-v2，新消息和回放消息均使用 v2 幂等键、分类策略和合同版本。
- [ ] 工具从统一运行配置或应用状态识别权威数据库，展示规范化路径、schema 版本、数据库身份摘要和活跃写入状态；候选路径不一致时 fail closed。
- [ ] schema 升级与画像回放分为两个显式步骤；回放工具不调用隐式 initialize，schema 不满足目标版本时只给出阻塞原因。
- [ ] 执行前创建可验证备份并完成恢复探针；无备份、备份校验失败或应用未进入安全维护状态时不得继续。
- [ ] dry-run 严格只读，分别报告可回放的 exhausted/client_error_400、succeeded/attempts=0、墓碑跳过、隐私阻止、撤回屏障、缺失消息和其他不处理类别，只输出计数、版本和审计 ID，不输出账户或正文。
- [ ] 正式回放为每条合格 v1 run 创建唯一 v2 run/任务；重复执行 dry-run、排队或 worker 收敛不会生成重复 observation、record 或任务。
- [ ] exhausted 400 与 succeeded/attempts=0 两个历史队列都被重新分类；无真实画像信号的旧消息可正常收敛为 v2 skipped，不强迫产生记录。
- [ ] 已墓碑消息、账户/内容级停止记录、已删除消息和已撤回画像永远不被重放或复活；第三方、否定、假设、角色扮演和敏感内容即使位于历史失败队列也必须被 v2 负例门拒绝。
- [ ] 回放严格按账户隔离；任务、运行、观察、四维记录和迁移报告都不能跨账户聚合证据或互相读取。
- [ ] worker 收敛后，权威数据库中目标队列没有遗留 pending/running；永久失败有明确终态和原因计数，相关账户通过画像 API 与 /account/profile 看见 v2 生成的合法记录。
- [ ] v1 运行和原始审计仍可只读追溯，v2 报告能关联来源运行但不复制私人正文。

## Test plan

- [ ] 以生产数据库的脱敏结构副本构造 schema 42、历史 400、succeeded/attempts=0、墓碑、隐私阻止、撤回和缺失消息测试夹具，禁止直接使用权威数据库跑测试。
- [ ] 验证权威数据库解析：配置路径正确、相对/绝对路径归一、仓库根目录误选、多候选冲突、数据库锁定和配置缺失均有确定结果。
- [ ] 验证 schema 门、备份校验和恢复探针；dry-run 前后比较数据库哈希/变更计数，证明零写入。
- [ ] 连续执行两次正式回放和多轮 worker，断言 v2 run、任务、observation 和 record 数量幂等。
- [ ] 分别验证 exhausted 400 与 succeeded/attempts=0 可回放，无信号旧消息转为 skipped，瞬态失败可恢复，永久失败不循环重试。
- [ ] 覆盖墓碑、账户停止记录、内容阻止、删除、撤回、第三方、否定和敏感负例，断言零复活、零跨账户读取。
- [ ] 通过 API 和页面完成回放后验收，并执行备份恢复演练，确认可回到回放前状态。
- [ ] 在发布运行手册中记录 dry-run、人工确认、正式排队、worker 收敛、验收查询和回滚顺序。

## Observability & rollback

- 每次操作生成唯一迁移审计 ID，并记录权威数据库身份摘要、schema 版本、备份校验结果、各候选类别计数、排队/成功/skipped/失败计数和开始结束时间；不记录私人正文。
- 提供按批次和账户边界的进度、队列深度、永久失败类别及未收敛任务告警；任何跨账户不变量失败立即停止后续批次。
- 回放采用小批次、可暂停的受监督队列。停止后保留 v1 和已完成 v2 结果，修复后按幂等键继续，不执行逆向覆盖。
- 发布前保留经恢复验证的数据库备份；若 schema、隔离、负例门或记录正确性失败，停止 worker、撤销尚未发布的 v2 投影，并从备份恢复。不得通过删除 v1 审计或恢复被用户撤回的内容实现回滚。
- 只有目标队列收敛、API/页面验收、备份恢复演练和脱敏迁移报告全部通过后，才能关闭本任务。
