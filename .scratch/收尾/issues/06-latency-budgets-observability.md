# 06 建立端到端时延预算、阶段埋点和有界降级

Status: completed
Priority: P0
Type: performance / reliability
Blocked by: 01, 02
Blocks: 07, 08, 09, 11

## 用户价值

用户不应面对 95—300 秒无反馈等待。系统要快速确认请求、持续显示真实阶段，并在外部服务过慢时有界结束或降级，而不是一直“思考中”或最终显示连接中断。

## 已观察证据

- 最近人味化改写运行约 87 秒和 297 秒后 `stream_interrupted`；生涯规划约 48 秒和 95 秒后同样中断。
- 简单问候也出现约 4.6—10 秒耗时。
- 学习、人味化等流程把本地检索、公开搜索、模型结构化输出、质量检查/重试串在单次用户等待路径中。
- 当前投影有总 duration，但缺少足以定位 300 秒发生在哪个阶段的统一细分。

## 要实现的纵向切片

为一次 run 建立统一阶段时钟和预算控制器。所有技能使用同一套阶段事件、截止时间、取消信号和脱敏指标；独立 I/O 可并行，非必要重试受总预算约束。

建议阶段：`queued`、`local_retrieval`、`public_search`、`model_generation`、`quality_check`、`repair`、`finalizing`。技能可增加子阶段，但不能绕开总预算。

## 实施步骤

1. 记录 run 排队、首个可见事件、各阶段开始/结束、模型首 token、终态耗时、超时/取消来源。
2. 指标只记录 ID、阶段、毫秒、结果码、模型/工具类别和计数；不记录消息、文档、搜索结果或密钥正文。
3. 设定并集中管理截止时间：每个外部调用有 timeout，重试使用剩余总预算；禁止嵌套组件各自无限重试。
4. 对彼此独立且都已确定需要的公开搜索并行执行；避免同一轮重复检索和重复质量检查。
5. 非流式技能至少在 1 秒内发出真实阶段事件；模型支持流式时尽早呈现草稿，不能把已完成正文扣留到全部软检查后。
6. 超预算时提交明确终态：可安全交付的草稿带警告交付；不可交付则说明失败阶段并允许重试。不得保持永久 running。
7. 提供本地性能摘要：p50/p95、超时率、各阶段占比、重试次数，不建立遥测外传。

## 验收标准

- [ ] 点击发送后 500ms 内出现用户消息，1 秒内出现 queued/running，2 秒内出现首个真实阶段状态。
- [ ] 注入 30 秒慢搜索时，界面持续显示正确阶段；阶段 timeout 到达后按策略降级，不等待 300 秒。
- [ ] 任一单次外部调用不得超过其配置 timeout；任一前台技能 run 在 120 秒内进入 done/failed/stopped 之一。
- [ ] 在确定性本地适配器下，普通聊天 p95 首 token ≤ 2 秒、终态 ≤ 5 秒；该指标用于防代码回归，不冒充线上模型 SLA。
- [ ] 同时需要两种公开来源时，总耗时接近较慢者而非两者之和，并保持结果顺序确定。
- [ ] 重试只在错误可重试且总预算足够时发生；阶段日志能解释每次重试。
- [ ] 人味化和生涯规划不再只显示笼统“思考中”；用户能看到检索/生成/检查/收尾阶段。
- [ ] 性能日志和测试报告不含用户内容或凭据。

## 反馈环

创建可控时钟/延迟适配器，分别注入快速、慢、超时、一次失败后成功。先写断言：阶段顺序、并行墙钟、总预算、终态和 UI 文案。再用脱敏真实运行采样确认 95/300 秒由哪些阶段构成，并把结果追加到 Comments。

## 约束与非目标

- 不用隐藏加载状态或提前显示假内容来“优化体感”。
- 不通过取消科学事实锁等硬安全门换速度。
- 不为单一慢请求引入远程监控平台。
- 不把所有技能强行设成相同质量策略；只统一预算和观测契约。
