## 1. 拆分原则

每张票交付一条窄而完整的用户路径，同时拥有所需的领域状态、持久化、接口、界面和测试。01 是先行的小范围准备重构，需证明完整历史读取路径行为不变；不另建纯数据库、纯 API 或纯前端基础票。

13 是最终真实模型与发布验收票，不能承担此前票遗漏的实现。每票自身的新数据生命周期、错误反馈、停止、恢复与必要合同同步均须完成。

PRD 的 P1–P6 是能力阶段，不作为六张横向票直接实施。下列十三张票按实际用户路径重组，编号按依赖顺序排列。

## 3. 执行前沿与依赖理由

- 初始前沿为 01；完成后开展 02。
- 02 完成后，03 和 07 不互相阻塞。
- 03 完成后，04、05、10、11 可以分别推进；仅表示依赖关系，不在本轮启动执行或子智能体。
- 06 等待 05 的正式档案和任务状态；08 等待 04 的用户控制与 07 的长期目标。
- 09 等待 06 的有效性/纠正/删除边界及 07 的路线，避免将已撤销判断用作个性化。
- 12 等待 08 的新目标续学与 10 的新材料授权，不需要等待公开查证功能。
- 13 等待 09、11、12，沿传递依赖覆盖全部票，不重复列出所有前置票。

05 不等待 07：单个理解难点也能形成知识点学情。07 不等待 05：可以先基于用户明确目标与必要探查建立路线。两条能力在 09 汇合。

## 4. 全部票据的共同要求

### 参考约束 C01

只借鉴参考项目的教学逻辑，禁止直接复制、搬运、改名移植其代码或将其作为项目依赖。提示词与接口合同按 BridGes 需求重新设计，优先调用本项目已有模块。交付说明记录借鉴的逻辑、采用的本项目接缝与自主实现范围，不以文本相似度测试代替代码审查。

### 技术与领域边界

开发和验证使用 conda `agent`。沿用现有 FastAPI、Pydantic、LangGraph、SQLite、模型网关、上下文编译、共享执行内核、任务队列和桌面聊天结构；新增依赖先核查已有能力。单代码文件不超过 500 行。

领域模型、外部协议、持久化和视图分别转换；学习领域拥有目标、证据与档案，队列只调度，模型不直接改表。账户隔离、模式锁定、附件与知识库分域、公开查询最小化和当前三日常模块合同均须保持。

学习证据的逻辑身份需包括账户、局部学习进展或长期目标、知识上下文、来源消息和版本。02 只实现局部进展，07 引入长期目标，后续通过引用关联；不得将会话 ID 改为全局学习目标 ID。

每张票拥有其新增状态的迁移、导出、备份、账户删除、引用失效与诊断上下文。新状态的业务提交与消息终态/任务登记按该票的原子边界处理；禁止把这些责任留给 13。

### 集成与旧代码退出

01 先保持读取与当前行为稳定。02 起的新模式能力在本批集成过程中验证，全部验收前不发布半成品；不新增长期双轨开关、旧业务兼容层或双写。

每票删除自己替代后不再使用的旧写入路径及孤儿代码。12 完成全仓旧执行入口审计与历史承接，不能成为此前各票拖延删除自己孤儿代码的理由。只读历史合同按读取义务保留。

### 检查与交付

- 修改前记录固定 Git 基线及相关已有失败；不覆盖其他工作的未提交变更。
- 先运行能复现行为的聚焦测试，再按项目要求完成 Ruff、mypy、pytest、依赖检查及相关完整检查。测试证明机制，不把模型自评当作教学效果。
- 前端变更完成类型检查、单元测试、适用的桌面端到端测试与构建；采用项目现有 npm 脚本，不能编造 `build:web` 等不存在的命令。
- 数据库变更执行项目实际迁移流程，需回填时另执行数据迁移，并验证幂等、导出、删除和恢复。生成合同按现有流程同步。
- 真实模型与外部服务的可得性、教学质量另记证据；不将替身响应包装成真实运行，不声称修复无关基线失败。
- 每票交付记录用户演示、合同/迁移变化、真实检查结果、限制、阻塞消费者接缝和 C01 审查。执行状态与验收状态分开。
