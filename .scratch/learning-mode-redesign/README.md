## 1. 拆分原则

每张票交付一条窄而完整的用户路径，同时拥有所需的领域状态、持久化、接口、界面和测试。01 是先行的小范围准备重构，需证明完整历史读取路径行为不变；不另建纯数据库、纯 API 或纯前端基础票。

13 是最终真实模型与发布验收票，不能承担此前票遗漏的实现。每票自身的新数据生命周期、错误反馈、停止、恢复与必要合同同步均须完成。

PRD 的 P1–P6 是能力阶段，不作为六张横向票直接实施。下列十三张票按实际用户路径重组，编号按依赖顺序排列。

## 3. 执行前沿与依赖理由

- 初始前沿为 01；完成后开展 02。
- 02 完成后，03 和 07 不互相阻塞。
- 03 完成后，04、05、10、11 可以分别推进；仅表示依赖关系，不在本轮启动执行或子智能体。
- 06 等待 05 的正式档案和任务状态；08 等待 04 的用户控制与 07 的长期目标。
- 09 等待 06 的有效性/纠正/删除边界及 07 的路线，避免将已撤销判断用作个性化。
- 12 等待 08 的新目标续学与 10 的新材料授权，不需要等待公开查证功能。
- 13 等待 09、11、12，沿传递依赖覆盖全部票，不重复列出所有前置票。

05 不等待 07：单个理解难点也能形成知识点学情。07 不等待 05：可以先基于用户明确目标与必要探查建立路线。两条能力在 09 汇合。

## 4. 全部票据的共同要求

### 参考约束 C01

只借鉴参考项目的教学逻辑，禁止直接复制、搬运、改名移植其代码或将其作为项目依赖。提示词与接口合同按 BridGes 需求重新设计，优先调用本项目已有模块。交付说明记录借鉴的逻辑、采用的本项目接缝与自主实现范围，不以文本相似度测试代替代码审查。

### 技术与领域边界

开发和验证使用 conda `agent`。沿用现有 FastAPI、Pydantic、LangGraph、SQLite、模型网关、上下文编译、共享执行内核、任务队列和桌面聊天结构；新增依赖先核查已有能力。单代码文件不超过 500 行。

领域模型、外部协议、持久化和视图分别转换；学习领域拥有目标、证据与档案，队列只调度，模型不直接改表。账户隔离、模式锁定、附件与知识库分域、公开查询最小化和当前三日常模块合同均须保持。

学习证据的逻辑身份需包括账户、局部学习进展或长期目标、知识上下文、来源消息和版本。02 只实现局部进展，07 引入长期目标，后续通过引用关联；不得将会话 ID 改为全局学习目标 ID。

每张票拥有其新增状态的迁移、导出、备份、账户删除、引用失效与诊断上下文。新状态的业务提交与消息终态/任务登记按该票的原子边界处理；禁止把这些责任留给 13。

### 集成与旧代码退出

01 先保持读取与当前行为稳定。02 起的新模式能力在本批集成过程中验证，全部验收前不发布半成品；不新增长期双轨开关、旧业务兼容层或双写。

每票删除自己替代后不再使用的旧写入路径及孤儿代码。12 完成全仓旧执行入口审计与历史承接，不能成为此前各票拖延删除自己孤儿代码的理由。只读历史合同按读取义务保留。

### 检查与交付

- 修改前记录固定 Git 基线及相关已有失败；不覆盖其他工作的未提交变更。
- 先运行能复现行为的聚焦测试，再按项目要求完成 Ruff、mypy、pytest、依赖检查及相关完整检查。测试证明机制，不把模型自评当作教学效果。
- 前端变更完成类型检查、单元测试、适用的桌面端到端测试与构建；采用项目现有 npm 脚本，不能编造 `build:web` 等不存在的命令。
- 数据库变更执行项目实际迁移流程，需回填时另执行数据迁移，并验证幂等、导出、删除和恢复。生成合同按现有流程同步。
- 真实模型与外部服务的可得性、教学质量另记证据；不将替身响应包装成真实运行，不声称修复无关基线失败。
- 每票交付记录用户演示、合同/迁移变化、真实检查结果、限制、阻塞消费者接缝和 C01 审查。执行状态与验收状态分开。

## 6. 并行执行建议

### 6.1 按已验收的依赖释放任务

先顺序完成 01、02，再安排并行。只看各票的直接阻塞票，不要求同一批的全部票同时完成。以下是依赖图允许的执行前沿；是否可以同时改代码，还要核对共享接缝。

| 已完成且验收通过的前置票 | 新可启动的票 | 并行含义 |
| --- | --- | --- |
| 无 | 01 | 初始只做历史读取与执行边界。 |
| 01 | 02 | 建立能演示的纯文字辅导路径。 |
| 02 | 03、07 | 理解验证与长期目标可以同时推进。 |
| 03 | 04、05、10、11 | 用户控制、后台诊断、材料教学、公开查证在依赖上互不阻塞；07 可继续。 |
| 05 | 06 | 档案管理可接续，不必等待材料或公开查证。 |
| 04、07 | 08 | 具备用户控制及目标后开始跨会话续学。 |
| 06、07 | 09 | 具备有效档案及路线后接入教学适应，不额外等待 08。 |
| 08、10 | 12 | 可开展历史主动续学与旧执行退出，不额外等待 09、11。 |
| 09、11、12 | 13 | 汇合后做最终真实模型旅程和发布验收。 |

排期时可采用七批作为简易视图：`01 → 02 → (03、07) → (04、05、10、11) → (06、08) → (09、12) → 13`。批次只是排期示例，不新增阻塞关系。例如 05 先完成就能开展 06，即使 10、11 仍在进行；08 和 10 完成就能开展 12，即使 09 尚未开始。

建议同时安排 2–3 张实施票，并由一位集成负责人协调共享修改、迁移顺序和合并。人手较少时，优先推进 `05 → 06 → 09` 与 `04、07 → 08 → 12` 两条汇合路径；10 是 12 的必要前置，应安排及时交付。这只是资源建议，不改变 11 的验收责任或 13 的发布门。

### 6.2 共享接缝的修改所有权

每张票仍须交付完整的用户路径。下表用于防止多个执行者同时修改同一合同，不另建横向基础票，也不把各票的集成工作推给 13。

| 可能同时推进的票 | 共享接缝 | 协作约定 |
| --- | --- | --- |
| 03、07 | 新学习读投影、聊天状态与合同生成 | 03 拥有理解验证与作答证据，07 拥有目标与路线。开始时确定各自字段及消费者合同，公共投影和生成产物由集成负责人顺序合并。 |
| 04、05 | 作答证据、回复终态与事务提交 | 04 拥有用户控制和小结，05 拥有诊断登记与档案。共享终态提交点由单一修改者协调，保留回复、证据和必要入队的原子性，不能各自增设一套提交路径。 |
| 04、05、10、11 | 导师上下文、来源投影和学习详情 | 各票拥有自己的行为及来源分支。沿用前置票已交付的公共合同；公共渲染、来源枚举和调度入口的变化集中合并，避免四票分别扩展一套相同逻辑。 |
| 06、08，随后 09 | 档案有效性、目标版本与读取快照 | 06 拥有纠正/删除及诊断失效，08 拥有目标切换与并发续学，09 消费有效档案。跨边界合同变化必须通知消费者并顺序集成，不能用共同会话 ID 代替各领域版本。 |
| 09、11、12 | 旧入口删除、能力注册与最终运行路径 | 12 提交实际删除清单，先核对其他票的消费者；不删除新模式仍使用的公共能力。09、11 的实现可并行，共享注册和旧执行收尾修改顺序合并。 |

SQLite 迁移编号、迁移执行顺序、共享 API 合同生成、统一导出/账户删除入口等由集成负责人协调。每张票先提交自己新增状态的生命周期变更和测试，再串行分配最终迁移顺序、生成公共产物并验证组合结果。不得让两个执行者同时修改同一份数据库或覆盖彼此的生成产物。

若发现前置票尚未交付必需接缝，应在票据 Comments 记录缺口并交回前置票；不能自行绕过，不能靠新增兼容层隐藏问题。普通文件冲突属于协调事项，不自动增加业务阻塞边。

### 6.3 认领、隔离与集成

1. 开始实施前，确认所有直接阻塞票已有验收证据且结果已集成；仅看到 `ready-for-agent` 不足以解除阻塞。在本票 Comments 记录执行者、固定 Git 基线、工作分支和本次负责的共享接缝。
2. 并行实施使用独立工作树或检出目录、独立分支，开发与检查均使用 conda `agent`。各自的测试数据库、对象目录、临时目录和服务端口应隔离；不并发修改同一工作目录，不使用真实账户库作为测试库。
3. 从前置票的已验收版本开始，先核对消费者合同再实现本票。需要变更共享合同或同一文件时，先明确单一修改者与合并顺序；其余执行者继续自身独立部分。
4. 每张票完成后交付用户演示、必要迁移/合同、真实检查结果、限制和 C01 审查，并验证自己与直接消费者的接缝。按依赖顺序集成；彼此独立的票可择先完成者合并，共享迁移和生成步骤仍顺序执行。
5. 独立检出中的聚焦测试、类型检查和构建可以并行。集成后的完整回归使用固定版本统一运行；13 的真实模型与外部服务评测登记模型、配置和预算，以受控并发避免同一供应商配额影响比较结果。
6. 已集成、已验收和已上线分别记录，不仅凭提交或测试数量宣称完成。13 验收前不发布半成品；本次票据发布不启动实施、工作树创建或生产发布。
